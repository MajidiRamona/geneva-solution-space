# Geneva Solution Space — website

Static site for the Geneva Solution Space (formerly the SDG Solution Space). Every page is
plain HTML generated by `build.py` from the text files in `content/`. No database, no server
code: any static host can serve it, and the editing panel at `/admin/` lets the team change
text, photos, events, partners and blog posts without touching code.

## Editing the site (no developer needed)

Open **`/admin/`** on the live site (for example `https://genevasolutionspace.org/admin/`)
and log in. The panel has four sections:

- **Blog posts** — write, edit and delete posts with a rich-text editor, cover image and date.
  Tick *Draft* to save a post without publishing it.
- **Events** — one entry per event. Events dated in the future appear on the homepage and on
  What We Host as *Upcoming*; once the date has passed they move to *Past events* on their own.
- **Partners** — the organizations on the ecosystem wheel and the Partners page, with logo,
  description and website.
- **Pages** — the text of every page, section by section, plus the site settings (address,
  email, footer links).

Formatting inside a text field: `**bold**`, `*italic*`, `[link text](/who-we-are/)`. Headings
have a plain part and an italic part because the design sets the second half in the serif
face.

Clicking **Publish** commits the change to the GitHub repository. The host rebuilds the site
from it within a minute or two, so a change is live shortly after saving.

## How it fits together

```
content/site.json          name, address, email, footer links
content/pages/<page>.json  the text of each page
content/partners/*.json    one file per partner
content/events/*.json      one file per event
content/posts/*.json       one file per blog post (body in Markdown)
templates/                 the two hero SVGs (gears, wheel spokes)
build.py                   turns content/ into index.html and <slug>/index.html
styles.css, script.js      design and behaviour
assets/                    photos, logos, uploads from the panel (assets/images/uploads)
admin/                     the editing panel (Decap CMS) and its field definitions
admin/bookings/            the staff booking dashboard (generated by build.py)
netlify/functions/         the booking API (TypeScript, runs on Netlify)
supabase/schema.sql        the bookings database table
```

`build.py` needs only Python 3. Run it locally with:

```bash
python3 build.py
```

then serve the folder (`python3 -m http.server 8000`) — links are root-relative, so open the
site through a server rather than as files. Bump `ASSET_VERSION` in `build.py` whenever
`styles.css` or `script.js` change, so visitors' browsers fetch the new file.

## Hosting

Both configurations below build the site on every push to `main`, which is what makes the
editing panel work: a save in the panel is a commit, and the commit triggers a rebuild.

### Netlify (current)

`netlify.toml` holds the build command. One-time setup in the Netlify dashboard:

1. **Link the repository:** Site configuration → Build & deploy → Continuous deployment →
   Link repository → this GitHub repo, branch `main`. The build command and publish
   directory are read from `netlify.toml`.
2. **Turn on Identity:** Site configuration → Identity → Enable. Under *Registration*, choose
   **Invite only**.
3. **Turn on Git Gateway:** Identity → Services → Git Gateway → Enable.
4. **Invite editors:** Identity → Invite users → enter their email addresses. Each person
   gets an email, sets a password, and can then log in at `/admin/`. No GitHub account is
   needed.

### Railway or another Docker host

The `Dockerfile` builds the pages and serves them with Caddy on `$PORT`. Point Railway at the
GitHub repository and it deploys on every push.

Railway has no built-in login for the panel, so switch the backend in `admin/config.yml` to
GitHub:

```yaml
backend:
  name: github
  repo: <owner>/geneva-solution-space
  branch: main
  base_url: https://<your-oauth-helper>   # a small OAuth relay, deployed once
```

Editors then log in with a GitHub account that has write access to the repository. The OAuth
relay is a tiny open-source service (search "decap cms github oauth provider"); it needs a
GitHub OAuth App's client id and secret as environment variables and can itself run on
Railway. Everything else — content, panel, build — is unchanged.

## Editing locally without logging in

```bash
npx decap-server            # in the site folder; proxies the panel to the local files
python3 -m http.server 8000 # in a second terminal
```

Uncomment `local_backend: true` in `admin/config.yml`, open
`http://localhost:8000/admin/`, and saves go straight to the files on disk. Re-comment the
line before committing.

## Forms

The contact and testimonial forms use Netlify Forms (`data-netlify` with a honeypot field).
Submissions appear in the Netlify dashboard under Forms. On another host these need a form
service or a small endpoint. Bookings no longer use Netlify Forms; see below.

## Bookings

The reservations page shows live availability for each space by the hour. Visitors pick a day
and hours (or whole days), see a price estimate and send a request. A request **holds the
time** straight away, so nobody else can request it, until staff approve or decline it.

**For staff:** open **`/admin/bookings/`** (or the *Bookings* button in the site editor) and
log in with your site-editor account.

- **Requests:** everything waiting for a decision, oldest first. *Approve* emails the
  requester a confirmation with a calendar invite; you can adjust the final price and add a
  message. *Decline* requires a short message and frees the time.
- **Calendar:** the week at a glance, all spaces. Click a booking to open it, or an empty hour
  to **block** time (maintenance, internal events). Blocked time shows as unavailable publicly.
- **All bookings:** search and filter, and **Export CSV** for invoicing.
- Every email has a link that lets the requester withdraw. Staff are emailed when that happens.
- To see all bookings in Outlook, Google or Apple Calendar, subscribe to
  `https://<site>/api/calendar.ics?token=<ICS_FEED_TOKEN>`. Anyone with that link can read it.

Spaces, opening hours, open days, capacity, prices, minimum notice and the first-time discount
are edited in the site editor under **Pages → Reservations**. They take effect on the next deploy.

**How it works:** `assets/js/booking.js` (public page) and `assets/js/bookings-admin.js`
(dashboard) call Netlify Functions in `netlify/functions/`. Those store bookings in a Supabase
(Postgres) database and send email through Resend. A database constraint makes overlapping
requests for the same space impossible, even when two arrive at the same moment. All times are
Geneva time. The Docker/Railway set-up below cannot run the booking API; bookings need Netlify.

### One-time setup

1. **Database:** create a free project at [supabase.com](https://supabase.com), with the
   region set to Europe (Zurich or Frankfurt). Open *SQL Editor → New query*, paste
   `supabase/schema.sql` and run it. Under *Project Settings → API*, copy the **Project URL**
   and the **service_role** key. The service key is secret and only goes into Netlify.
2. **Email:** create an account at [resend.com](https://resend.com), add the domain
   `genevasolutionspace.org` and add the DNS records it shows. Then create an API key.
3. **Netlify:** *Site configuration → Environment variables*:

   | Variable | Value |
   |---|---|
   | `SUPABASE_URL` | Project URL from step 1 |
   | `SUPABASE_SERVICE_KEY` | service_role key from step 1 |
   | `RESEND_API_KEY` | API key from step 2 |
   | `MAIL_FROM` | optional, default `Geneva Solution Space <bookings@genevasolutionspace.org>` |
   | `STAFF_EMAIL` | optional: who gets new-request emails (default: the staff email in the CMS, then the site email) |
   | `ICS_FEED_TOKEN` | a long random string (e.g. `openssl rand -hex 24`) for the calendar feed |
   | `BOOKING_ADMINS` | optional: comma-separated emails allowed to manage bookings. If unset, every site editor can. |

   Then trigger a deploy. Staff use their existing Identity invites.

### Running it locally

```bash
npm install
python3 build.py
npx netlify-cli dev     # serves the site and /api/* on http://localhost:8888
```

Put the variables above in a `.env` file (not committed) to point at a test Supabase project.
Without `RESEND_API_KEY`, emails are printed to the terminal instead of sent.
`npm run check` type-checks the functions.
